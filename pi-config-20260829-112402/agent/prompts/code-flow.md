# 通用编码工作流

你要完成一次编码任务。任务：`$ARGUMENTS`

本流程按阶段依次加载 skills：`karpathy-coder`、`codebase-design`、`tdd`、`code-review`。每个阶段开始前用 `skill` 工具加载对应 skill，用到哪个加载哪个。

全程遵守四条铁律（karpathy-coder 原则）：
1. **先想后写**——不臆测、不隐藏困惑、显式抛出权衡，拿不准就问。
2. **最小实现**——只做被要求的事，不要投机性抽象、可配置性、为不可能场景写的错误处理。
3. **外科手术式改动**——只碰必须碰的，不顺手"改进"旁边的代码；你造成的死代码要清掉，别人遗留的只提不说。
4. **目标驱动**——每个步骤都要有可验证的检查，循环直到验证通过。

## 阶段 0：澄清与假设

用 `skill` 工具加载 `karpathy-coder`。然后：
- 复述你对任务的理解；显式列出所有假设。
- 有歧义就列出多种解读让用户选，**绝不默默选一种**。
- 遇到困惑就停下，把困惑命名出来，问用户。
- 如果存在明显更简单的方案，直接说出来并给权衡。

## 阶段 1：定义可验证目标（规格捕获）

按"Step → verify: check"格式写出计划：

```
1. [步骤] → verify: [怎么验证]
2. [步骤] → verify: [怎么验证]
...
```

**这份清单就是规格（spec）。** 把它写进工作区文件（优先 `.scratch/SPEC.md`），后续 code-review 的 Spec 轴用它对照。每个目标必须有可验证的检查，禁止"实现xxx"这种空泛写法。此时确定 diff 基准（工作起点，如 `HEAD`），供阶段 5 使用。

## 阶段 2：架构设计（条件触发）

**只有当接口形状存疑时才做**：任务涉及多个模块、seam 位置不清楚、模块深度（小接口 vs 大实现）拿不准、或复杂逻辑预计超过约 20 行。简单任务直接跳过进入阶段 3。

用 `skill` 工具加载 `codebase-design`：
- 用它的精确词汇：module、interface、depth、seam、adapter、leverage、locality（不要用 component/service/API/boundary）。
- 设计**深模块**：小接口 + 大量实现；做"删除测试"判断模块是否值得存在；只有一个 adapter 就别引入 seam。
- 定下每个模块的 seam 位置。

**把"被测 seams"写下来并与用户确认**——这是 tdd 的前置门槛：测试只能写在已确认的 seams 上。

## 阶段 3：TDD 实现

用 `skill` 工具加载 `tdd`。然后：
- **垂直切片**，一个循环一次：写一个失败测试 → 写刚好能通过的最小实现 → 跑测试确认红→绿 → 再下一个。
- 只在阶段 2 确认的 seams 上测试；测试走公共接口，不摸内部实现。
- 禁止反模式：tautological tests（期望值必须来自独立已知来源，不能照抄代码逻辑重算）、implementation-coupled（mock 内部协作方/测私有方法）、horizontal slicing（不要一次写完所有测试再写实现）。
- **重构不是本循环的一部分。** 循环中发现的设计问题只记录，留给阶段 4。

## 阶段 4：复盘与重构

- 处理阶段 3 记录的问题。
- 按 codebase-design 原则收紧：接口是否还能更小、实现是否藏得够深、删除测试是否成立。
- 重构后**重跑全部测试**必须全绿。

## 阶段 5：审查

用 `skill` 工具加载 `code-review`：
- 审查代码，并出具审查报告

## 阶段 6：修复与交付

- 修复审查发现：标准违规、规格偏差、越界功能。**注意**：审查说"实现过度复杂"不算违规，别用新复杂度去凑。
- 修复后重跑全部测试。
- 提交前最后过一遍 karpathy 四原则自检。
- 交付总结：
  - 改了什么（每行改动应能追溯回任务）
  - 验证了什么（测试覆盖、如何跑）
  - 遗留了什么（已知边界、未确认的假设）

## 收尾模板

```markdown
## 交付总结
**改动**：……
**验证**：……（测试命令 + 结果）
**审查**：Standards X 项 / Spec Y 项，已全部修复/说明
**遗留**：……
```

## 流程速查

| 阶段 | skill | 关键动作 | 产出 |
|---|---|---|---|
| 0 澄清 | karpathy-coder | 显式假设、抛出权衡、问 | 无歧义的任务理解 |
| 1 目标 | karpathy-coder | Step→verify 清单 | `.scratch/SPEC.md`（规格） |
| 2 架构 | codebase-design | 深模块 + seam，**seams 与用户确认** | 模块/接口/seam 清单 |
| 3 实现 | tdd | 垂直切片红→绿循环 | 测试全绿 |
| 4 复盘 | codebase-design | 收接口、藏实现、删测试 | 重构后测试仍绿 |
| 5 审查 | code-review | 审查报告 | 出具审查报告 |
| 6 交付 | — | 修复→重跑→四原则自检 | 交付总结 |

**例外**：纯提问/研究/一句话修 typo 等琐碎任务，跳过阶段 2-5，直接做并说明为什么。
